# Первая итерация backend без БД

Стек по решению команды: Spring Boot, Kotlin, Gradle. Frontend разрабатывается отдельно и взаимодействует с backend по REST/JSON. Это описание объёма работ; Spring-приложение и API пока не реализованы.

## Результат первой итерации

Пользователь выбирает группу поставщика, загружает известные Excel-файлы, получает отчёт проверки и общую таблицу товаров. Можно найти товар, посмотреть его доступные продажи, остатки, поставки и условия заказа.

IEK и Systeme Electric используются как две условные группы поставщиков текущего набора. Юридического справочника контрагентов в исходных данных нет. Обработка новых групп в дальнейшем добавляется отдельным профилем импорта.

Первая итерация проверяет путь Excel → нормализованные данные → JSON → таблица. Она ещё не закрывает все обязательные требования ТЗ к расчёту заказа.

## Пользовательский сценарий

1. Выбрать `iek` или `systeme`.
2. Загрузить обязательный базовый файл и, при наличии, дополнительные файлы в подписанные поля формы.
3. Указать/подтвердить дату среза данных. Она может быть неизвестна; дата загрузки не подменяет дату отчёта.
4. Получить `import_id`, число прочитанных товаров и предупреждения с координатами в Excel.
5. Открыть таблицу, искать по коду/артикулу/названию, фильтровать строки с замечаниями.
6. Открыть товар и увидеть месячную историю, партии в пути и происхождение показателей.

Новая загрузка создаёт отдельный импорт. Перезапись существующего набора и дозагрузка отдельных файлов в существующий импорт в первую итерацию не входят: обновление делается новым комплектом.

## Поддерживаемые файлы

Пользователь явно указывает роль файла через поле формы. Сервер проверяет листы и заголовки: название файла само по себе не доказывает правильный формат. Поддерживаются известные структуры `.xlsx`, а не произвольные таблицы с конструктором сопоставления колонок.

| Группа | Роль multipart | Файл | Обязателен |
| --- | --- | --- | --- |
| Systeme Electric | `snapshot` | `Товар в пути_SystemElectric на 22.09.2026.xlsx`, основной лист `TDSheet` | Да |
| Systeme Electric | `order_terms` | `MOQ SystemElectric.xlsx` | Нет |
| IEK | `monthly_sales` | `Ежемесячные продажи в количественном выражении за последние 2 года.xlsx` | Да |
| IEK | `monthly_stock` | `Ежемесячные остатки продукции за последние 2 года  ИЭК.xlsx` | Нет |
| IEK | `incoming_shipments` | `Путь ИЭК 22.09.2026.xlsx` | Нет |
| IEK | `order_terms` | `MOQ  ИЭК.xlsx` | Нет |

Если дополнительный файл отсутствует, соответствующие поля остаются неизвестными и это видно в отчёте. Если дополнительный файл был отправлен, но его структура неверна, весь новый импорт отклоняется: файл не игнорируется молча.

Детальная динамика продаж, отдельные файлы/вспомогательные листы сезонности и отдельные месячные отчёты Systeme подключаются в следующих итерациях. В первой версии не предлагать для них поля загрузки и возвращать явную ошибку при неподдерживаемом типе файла. Это ограничение первой итерации, а не объявление этих источников ненужными для ТЗ.

## Что нормализует backend

| Сущность в памяти | Содержание |
| --- | --- |
| `SupplierProfile` | Идентификатор группы, название, поддерживаемые и обязательные роли файлов. |
| `ImportedDataset` | ID, группа, время создания/истечения, даты данных, сведения о файлах, товары и отчёт проверки. |
| `Product` | Внутренний ID внутри импорта, код 1С, артикул, название, единица и доступные исходные атрибуты. |
| `MonthlySales` | Товар, месяц, исходное количество, полнота периода и источник. |
| `StockObservation` | Товар, период/дата, вид остатка, количество и источник. |
| `IncomingShipment` | Товар, количество, номер/дата заказа, ожидаемая дата или крайний срок, исходный заголовок. |
| `OrderTerms` | Кратность и минимальная отгрузка как отдельные поля с источником. |
| `ImportIssue` | Код проблемы, серьёзность, файл, лист, строка/ячейка и понятное сообщение. |

Ключ сопоставления — строковый код 1С. В набор товаров входит объединение кодов всех поддерживаемых загруженных файлов, включая позиции, присутствующие только в остатках или поставках. При отсутствии истории продаж она остаётся неизвестной. Пустые коды и противоречивые дубли попадают в отчёт; строки не теряются без объяснения.

Все количества сохраняются с исходным знаком. В Kotlin для количества, кратности и стоимостных значений использовать `BigDecimal`, для месяца/даты `LocalDate`, для технического ID — UUID. Ошибка Excel, пустая ячейка и настоящий ноль различаются.

Формулы исходных файлов не исполняются как произвольный код. Для исходных вычисляемых значений читаются сохранённые результаты и отмечаются отсутствующий кеш/ошибки. Внешний прайс из кэша MOQ не становится автоматически ещё одним каталогом товаров. На стороне сервиса не выполняется обновление внешних ссылок.

## Таблица для frontend

| JSON-поле строки | Смысл |
| --- | --- |
| `id` | ID товара внутри импорта для открытия карточки. |
| `erp_code` | Исходный код 1С, строка. |
| `supplier_article` | Артикул, `null`, если неизвестен. |
| `name`, `unit` | Название и единица учёта; единица может быть неизвестна. |
| `sales_month` | Месяц выбранного показателя продаж. |
| `sales_qty`, `sales_period_status` | Исходные продажи за этот месяц; статус `complete`, `partial` или `unknown`. |
| `stock_as_of_date` | Дата текущего снимка, если установлена. |
| `free_stock_qty` | Актуальный свободный остаток. У IEK из перечисленных файлов неизвестен. |
| `historical_stock_period`, `historical_stock_kind`, `historical_stock_qty` | Последний доступный исторический остаток, его период и вид. Для IEK — начало месяца. |
| `incoming_qty`, `incoming_status` | Известная сумма ожидаемых партий и статус полноты: `known`, `partial` или `unknown`. Пустой файл/пропуски не превращаются автоматически в нулевой итог. |
| `order_multiple` | Подтверждённая кратность, если загружена и корректна. |
| `minimum_shipment_qty` | Значение минимальной отгрузки IEK, отдельное от кратности. Детали исходной семантики в карточке/отчёте. |
| `has_issues`, `issues` | Замечания по этой строке. |

Для совместимости с `docs/front data.txt` строка также содержит `supplier_id` и `supplier_name`. Сведения об импорте передаются в обёртке ответа. Количества в JSON — числа или `null`, как в ранее предложенном контракте; вычисления с точными десятичными значениями выполняются на backend. Коды остаются строками. Суммы денег при появлении стоимостного расчёта передаются десятичными строками или `null`.

По умолчанию колонка продаж показывает последний подтверждённый полный месяц, общий для базового отчёта. Если полнота не установлена, показывается последний доступный месяц с явной отметкой `unknown`, а не выдаётся за полный. Самая свежая дата среди разных файлов не назначается автоматически всему набору.

В карточке товара возвращаются полная доступная месячная история, отдельные партии поставок и исходные складские компоненты Systeme. Стоимостной атрибут `СС реал`, категория и прочие неоднозначные показатели показываются с исходным названием, без превращения в подтверждённую закупочную цену или ABC/XYZ.

`recommended_qty`, прогноз, ABC/XYZ, срочность и покрытие относятся к следующей итерации. В первой таблице их не показывать как вычисленные; если frontend уже зарезервировал колонки, использовать `null` и состояние «Не рассчитано». Нулевой заказ не означает отсутствие расчёта. В существующем эскизе `docs/front data.txt` уже есть `order_qty` и `explanation`: в первой версии это `order_qty: null`, `explanation: null`, дополненные явным `calculation_status: "not_calculated"`. `issues` объясняет проблемы импорта и не подменяет объяснение рекомендации.

## REST API первой итерации

Это предлагаемые маршруты, а не уже работающий API.

| Метод и путь | Результат |
| --- | --- |
| `GET /api/suppliers` | Две поддерживаемые группы и описание полей загрузки/обязательных файлов. |
| `POST /api/imports` | Multipart с `supplier_id`, метаданными дат и файлами по ролям. Синхронный разбор, успешный ответ `201`: `import_id`, статус и сводка. |
| `GET /api/imports/{id}` | Файлы, даты, статус, число товаров, отчёт ошибок/предупреждений, `expires_at`. |
| `GET /api/imports/{id}/products` | Строки таблицы. Параметры `query`, `has_issues`, `page`, `size`, `sort`; ответ содержит `items`, `page`, `size`, `total_elements`. |
| `GET /api/imports/{id}/products/{productId}` | Детали товара, история, поставки и источники. |
| `DELETE /api/imports/{id}` | Удалить набор из памяти. |

При невалидной структуре/неподдерживаемом файле возвращается `422` с понятным отчётом. При превышении лимита загрузки — `413`. Истёкший, неизвестный или недоступный текущей сессии импорт возвращает `404` с сообщением о необходимости новой загрузки. Сортировка допускает только заранее перечисленные поля.

Файловая структурная ошибка блокирует публикацию нового набора. Проблемы отдельных значений возвращаются как замечания, поля остаются неизвестными либо конфликтными. Строка без пригодного кода остаётся в отчёте с исходными координатами и учитывается в `unmapped_rows_count`. Число предупреждений и число отброшенных из предметного представления строк должны быть видны.

## Хранение без БД

`InMemoryDatasetStore` хранит нормализованные наборы в памяти, например по UUID в `ConcurrentHashMap`. Готовый набор публикуется целиком после разбора; читатели не видят частично заполненную коллекцию.

- Каждый импорт независим; нет одной глобальной переменной «текущий поставщик».
- Импорт привязан к браузерной сессии. Это изоляция данных первой версии, а не система пользователей/ролей.
- Время жизни, максимальные размеры загрузки, число строк и число импортов ограничены настройками; истёкшие наборы удаляются.
- Перезапуск backend удаляет все данные и сессии. Frontend сообщает о необходимости загрузить файлы снова.
- Первый запуск рассчитан на один экземпляр backend. Общая память нескольких серверов не предполагается.
- Временные файлы загрузки очищаются после разбора. Долговременное хранение оригиналов и истории не входит в эту версию.
- Невалидная новая загрузка не удаляет ранее успешно загруженный набор.

## Организация Kotlin-кода

Достаточно одного приложения и нескольких пакетов:

```text
supplier/   SupplierProfile, SupplierController
excel/      SupplierExcelParser, SystemeExcelParser, IekExcelParser
imports/    ImportService, ImportController, ImportValidation
dataset/    InMemoryDatasetStore, ProductQueryService
model/      нормализованные data class
api/        DTO и общий формат ошибок
```

Парсеры поставщиков реализуют общий интерфейс, но знают собственные листы/шапки. Контроллеры работают с нормализованной моделью и не разбирают Excel. Следующий модуль `calculation/` получает готовый набор, поэтому алгоритм не зависит от букв столбцов исходника.

Контракт JSON и небольшие примеры ответов для двух групп должны быть согласованы с frontend до реализации экранов. CORS и обмен cookie сессии настраиваются под адрес frontend. Версии Spring Boot/Kotlin/JDK и XLSX-библиотека выбираются при создании проекта; БД, JPA и миграции для этой итерации не требуются.

## Критерии готовности

1. Для каждой группы загружается минимальный набор и набор со всеми поддерживаемыми дополнительными файлами.
2. Коды с ведущими нулями и `_` не меняются, товары сопоставляются по коду, пропуски и дубли видны.
3. IEK-остаток на начало месяца не попадает в `free_stock_qty`.
4. Пустое количество, ошибка Excel и настоящий ноль различаются в результате импорта.
5. Кратность Systeme и минимальная отгрузка IEK сохраняются раздельно.
6. Неподдерживаемый или повреждённый файл даёт понятную ошибку, старый импорт остаётся доступным.
7. Таблица поддерживает поиск, пагинацию и открытие карточки товара для frontend.
8. Одновременно загруженные наборы и две браузерные сессии не смешиваются.
9. После удаления/истечения/перезапуска frontend получает предсказуемый ответ о недоступном наборе.

Проверки реализации: модульные тесты парсеров на небольших XLSX-примерах, тесты объединения/валидации и интеграционный сценарий upload → products → detail → delete. Полные реальные файлы используются для контрольного импорта, без зависимости обязательных CI-тестов от их локального наличия.

## Следующие итерации

| Итерация | Добавление | Проверяемый результат |
| --- | --- | --- |
| 1 | Импорт, проверка, память, таблица | Можно загрузить и объяснить каждое исходное значение. |
| 2 | Прозрачный базовый расчёт | Пользователь задаёт срок поставки и период закупок как параметры модели. По достаточным данным рассчитываются спрос на горизонт, остаток, учитываемый путь и количество заказа. Начать с Systeme. Для IEK в текущих Excel отсутствует актуальный свободный остаток; до появления подходящей выгрузки результат недоступен, а не нулевой. |
| 3 | Полная история и устойчивый спрос | Подключаются динамика и сезонность, обработка разовых операций/возвратов, сезонность и рост. Источники одного факта сверяются, а не складываются. |
| 4 | Stockout и полнота ТЗ | Оценка упущенного спроса с явно указанной точностью; категории/рост участвуют в расчёте; клиентский критерий требует анонимного ID либо отдельного тестового набора. |
| 5 | Работа с заказом | Ручная корректировка с причиной, подтверждение, экспорт. Объяснение по каждой строке начинается уже в итерации 2. |

Сохранение между перезапусками, БД, авторизация, LLM, автоматическая рассылка и интеграция с 1С обсуждаются отдельно по необходимости. Они не нужны для завершения первой итерации.
