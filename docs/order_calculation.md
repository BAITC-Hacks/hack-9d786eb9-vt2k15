# Расчёт рекомендаций по заказу

Backend рассчитывает рекомендации из последнего загруженного снимка Excel через `GET /api/orders`. Расчёт читает снимок один раз, не изменяет импортированные DTO и не отправляет заказы поставщикам. БД, сохранение утверждения и автоматическая отправка в этот endpoint не входят.

Это наша прозрачная реализация расчёта. PDF ТЗ требует учитывать сезонность, устойчивый рост, возможный упущенный спрос, разовые крупные продажи и формировать рекомендации по поставщикам, но **не задаёт конкретных формул и сроков 30/60/90 дней**. Описанные ниже пороги и методы — решения текущей реализации, которые нужно проверять на истории и согласовывать с закупщиком.

Код: [OrderPlanningController.kt](../src/main/kotlin/kz/hackalem/backend/OrderPlanningController.kt), [OrderPlanningService.kt](../src/main/kotlin/kz/hackalem/backend/OrderPlanningService.kt), [DemandForecastEngine.kt](../src/main/kotlin/kz/hackalem/backend/DemandForecastEngine.kt), [OrderPlanningData.kt](../src/main/kotlin/kz/hackalem/backend/OrderPlanningData.kt). Структура входных данных описана в [excel_models.md](excel_models.md).

## 1. Вызов API

Сначала загрузить полный комплект одного или обоих поставщиков через `POST /api/excel`, затем запросить расчёт:

```http
GET /api/orders?leadDays=60&reviewDays=30&historyMonths=12&forecastGrowthPercent=0&anomalyMultiplier=3&supplierId=systeme
```

60 дней поставки и 30 дней до следующего пересмотра в этом запросе — **пример выбранных пользователем параметров**, не значения по умолчанию.

| Query-параметр | Обязательность / default | Диапазон и смысл |
|---|---|---|
| `leadDays` | Обязателен, default отсутствует | Целое 0–365: срок поставки в календарных днях |
| `reviewDays` | Обязателен, default отсутствует | Целое 1–365: интервал до следующего пересмотра заказа |
| `historyMonths` | Необязателен, default `12` | Целое 6–36: длина окна полных месяцев истории |
| `forecastGrowthPercent` | Необязателен, default `0` | Число от −100 до 300: дополнительный сценарный прирост в процентах |
| `anomalyMultiplier` | Необязателен, default `3` | `BigDecimal`, строго больше 1 и не больше 100: множитель среднего количества остальных документов для поиска разовой крупной продажи |
| `supplierId` | Необязателен | `iek` или `systeme`; без параметра рассчитываются все поставщики текущего снимка |
| `category` | Необязателен | Точное совпадение исходного кода категории, например `1`; пока это фильтр, а не набор правил расчёта |

Горизонт `H = leadDays + reviewDays`, то есть 1–730 календарных дней. Дополнительный прирост преобразуется в множитель `1 + forecastGrowthPercent / 100`; это отдельный параметр от тренда истории и роста из исходного отчёта.

| HTTP-код | Когда возникает |
|---|---|
| `200` | Расчёт выполнен; `items` может быть пустым, причины нужно смотреть в `skipped`, `review` и сводках |
| `400` | Нет обязательного параметра, неверный тип/диапазон либо неизвестный `supplierId` |
| `409` | Ещё не было успешной загрузки Excel |
| `404` | Запрошенный поставщик отсутствует в текущем снимке |

Неизвестная категория не вызывает `404`: фильтр просто может оставить ноль товаров. После загрузки только IEK прежний Systeme в снимке отсутствует, поскольку загрузка заменяет весь снимок, а не объединяет его с предыдущим.

## 2. Как связаны источники

Адаптеры [IekOrderSource.kt](../src/main/kotlin/kz/hackalem/backend/IekOrderSource.kt) и [SystemeOrderSource.kt](../src/main/kotlin/kz/hackalem/backend/SystemeOrderSource.kt) соединяют товары по строковому `productCode` — коду 1С. В выборку попадает объединение кодов из пяти товарных отчётов; строка без кода не может быть надёжно сопоставлена и отмечается предупреждением. Сезонность задаётся на уровне поставщика.

| Источник | Роль для IEK | Роль для Systeme Electric |
|---|---|---|
| Ежемесячные продажи | Основная история `sales` | Основная история `monthlySales`; только при отсутствии строки используется история TDSheet |
| Динамика продаж | Дата актуальности данных, размеры документов для выбросов; запасной источник истории | То же; не прибавляется к месячным продажам |
| Ежемесячные остатки | История возможного stockout; для наличия — остаток последнего общего месяца отчёта | История возможного stockout; не заменяет текущий свободный остаток |
| Путь / сводный отчёт | Количества по партиям и `expectedBy` из заголовков | Свободный остаток, путь, категория, исходный рост; также запасная месячная история |
| MOQ | Минимальная разрешённая отгрузка | Кратность из отдельного MOQ, а не из дублирующей колонки месячных продаж |
| Сезонность | Предпочтительно нижний нормализованный коэффициент; иначе итоговый коэффициент основного блока | Итоговый коэффициент отдельного файла; при его отсутствии/неположительности — среднее доступных положительных годовых коэффициентов |

Совпадающие дубликаты не суммируются; противоречивые дубликаты значимых для расчёта данных и несовместимые единицы блокируют расчёт товара. `supplierArticle` и название — дополнительные сведения, а не замена кода 1С. Явно обозначенная закупка IEK бухтами при учёте метрами без коэффициента пересчёта блокируется.

Скрытые сезонные листы, контрольные итоги, стоимость `СС реал`, вес, исходный `Запас` и другие поля остаются в импортированных DTO. Они не складываются с основными источниками и не все являются входами текущей формулы. В частности, стоимости заказа, страхового запаса и новой ABC/XYZ-классификации эта версия не рассчитывает.

### Дата данных и остаток

`dataThrough` для каждого поставщика — максимальная известная дата операции в его динамике продаж. Дата сервера и дата в имени файла её не подменяют. Если дату определить нельзя, товары этого поставщика уходят в `skipped`.

Для Systeme используется `availableStock` из TDSheet. Если он отсутствует, но известны `stock` и `reservedStock` из той же строки, допускается `stock − reservedStock` с предупреждением. Если ни один вариант недоступен, товар пропускается. Резерв повторно из свободного остатка не вычитается; складские компоненты не прибавляются к нему.

Для IEK используется **остаток на начало последнего общего месяца отчёта**. Если у товара значение этого месяца пустое, более ранний ненулевой остаток не подставляется. Это оценка, а не текущий свободный остаток: резервов и движений после начала месяца в этой величине нет. Ответ содержит `stock_basis = "MONTH_OPENING"`, `stock_month` и предупреждение. Если месяц остатка позднее месяца `dataThrough`, товар пропускается как несогласованный по времени.

## 3. Прогноз спроса по шагам

### 3.1. Окно истории

Берутся последние `historyMonths` **полных месяцев** относительно `dataThrough`. Например, при `dataThrough = 2026-09-22` последний месяц истории — август 2026. Если данные датированы последним календарным днём месяца, этот месяц включается.

Неизвестные значения и отсутствующие месяцы исключаются с предупреждением; они не становятся нулями. Для результата нужны минимум три известных полных месяца внутри окна. Известные нули — полноценные наблюдения. Полностью неизвестная история не даёт нулевой прогноз: результат для товара будет в `skipped`.

Если месячная история товара отсутствует целиком, возможен запасной расчёт по расходным накладным. Он использует полные месяцы общей истории выгрузки и требует хотя бы одной операции товара с известным количеством в окне. Отсутствие операций внутри этого общего периода принимается за нулевые продажи **с явным предупреждением о допущении полноты выгрузки**. Если в месяце есть операция с неизвестным количеством, месяц исключается. Наличие месячного отчёта с пустыми ячейками не разрешает незаметно заменить их динамикой.

### 3.2. Разовые крупные продажи

[SaleAnomalyDetector.kt](../src/main/kotlin/kz/hackalem/backend/SaleAnomalyDetector.kt) работает отдельно для каждого SKU каждого поставщика, только в том же окне полных месяцев. Строки документов типа `Расходная накладная` группируются по **полной календарной дате (`LocalDate`, включая год) и номеру документа**. Внутри документа количества складываются со знаком: отрицательная строка уменьшает итог. Разные даты с повторяющимся номером не объединяются. Строки без даты или номера пропускаются с предупреждением; документ хотя бы с одним неизвестным количеством целиком исключается из детектора. Возвраты и нулевые итоги не считаются положительными покупками.

Нужны минимум пять полных документов с положительным итогом для этого SKU. Если их меньше, очистка по документам не выполняется и возвращается предупреждение; сам прогноз при достаточной месячной истории возможен. Каждый документ сравнивается со средним **всех остальных** таких документов в окне; проверяемый документ в среднее не входит:

```text
comparisonOrderCount = N − 1
averageOtherQuantity = (Σ(documentQuantity) − q) / (N − 1)
thresholdQuantity = averageOtherQuantity × anomalyMultiplier
anomaly ⇔ q > thresholdQuantity
```

По умолчанию `anomalyMultiplier = 3`, как выбрано пользователем. Например, для количеств `10, 10, 10, 10, 100` у документа на 100 среднее остальных равно 10, порог — 30: документ признаётся разовым. Равенство порогу не является аномалией. Проверки используют исходный набор подходящих документов, без последовательного удаления ранее найденных аномалий.

До восстановления возможного stockout и расчёта тренда известные месячные продажи очищаются:

```text
anomalyQuantity_m = Σ(количества аномальных документов месяца)
qClean_m = max(0, rawMonthly_m − anomalyQuantity_m)
excludedOutlierQuantity = Σ(max(0, rawMonthly_m) − qClean_m)
```

Если сумма аномалий превышает месячное количество, результат ограничивается нулём с предупреждением о несогласованности. Отрицательные месячные продажи тоже ограничиваются нулём с предупреждением. Исходные DTO не меняются; динамика не прибавляется поверх месячных продаж.

`excludedOutlierQuantity` — **фактическое уменьшение положительной месячной истории**. Оно может быть меньше суммы количеств аномальных документов из-за возвратов или расхождений источников. Неизвестные месяцы уже исключены из истории; найденные для них документы не включаются в `excludedSales` и не увеличивают исключённое количество. Список документов и их пороги доступны в ответе, см. раздел 5.

ID клиента в данных нет. Поэтому несколько крупных покупок одного клиента в разных документах объединить невозможно; это ограничение относительно ТЗ остаётся.

### 3.3. Сезонность и возможный stockout

Положительные сезонные коэффициенты нормализуются делением на их среднее. Для отсутствующего или неположительного коэффициента используется нейтральное значение 1 с предупреждением. Это общие исходные коэффициенты поставщика: они не связаны с отдельными транзакциями и после удаления аномальных продаж не пересчитываются. Обозначим итоговый коэффициент месяца `s_m`, фактическое количество дней — `days_m`, очищенные продажи — `q_m`.

```text
Спрос в день без сезонности: d_m = q_m / days_m / s_m
```

Ровно нулевой месячный остаток — признак **возможного** отсутствия товара. Пустой остаток таким признаком не считается. По известным продажам месяцев, не отмеченных нулевым остатком, находится базовый спрос:

```text
b_ref = Σ(q_m / s_m) / Σ(days_m)
```

Для месяца с нулевым остатком продажи восстанавливаются вверх до:

```text
q_restored_m = max(q_m, b_ref × days_m × s_m)
```

Если месяцев для сравнения нет, восстановления нет и добавляется предупреждение. `stockoutAdjustment` — сумма добавленных количеств **в истории**, а не отдельная надбавка к будущему заказу. Месяцы с неизвестным остатком могут попасть в базу сравнения: это ещё одно допущение, а не доказательство наличия товара.

После восстановления дневная база по всем известным месяцам окна:

```text
baseDailyDemand = Σ(q_restored_m / s_m) / Σ(days_m)
```

Длина каждого месяца учитывается фактически, в том числе февраль и високосные годы. Деления всех месяцев на 30 нет.

### 3.4. Устойчивый рост

Если известны все шесть последних последовательных полных месяцев, сравниваются дневные продажи без сезонности последних трёх с предыдущими тремя. Коэффициент тренда — отношение средних этих групп. Он применяется только когда:

- среднее и медиана обе показывают рост минимум на 10% либо снижение минимум на 10%;
- хотя бы две из трёх попарно сравниваемых месяцев подтверждают это направление с тем же порогом.

Одиночный скачок сам по себе не подтверждает устойчивость. При неполных шести месяцах или невозможности корректно сравнить с нулевой базой `trendFactor = 1`. Подтверждённый коэффициент ограничивается диапазоном 0,5–2; ограничение сопровождается предупреждением.

Если в окне найдены аномальные документы, `sourceGrowthFactor = 1`. Если исходный коэффициент роста был задан, его отключение сопровождается предупреждением: сохранённый в отчёте рост рассчитан до очистки, поэтому использовать его повторно нельзя. Вычисленный тренд при этом определяется по очищенной истории после восстановления возможного stockout; дополнительный пользовательский процент продолжает применяться.

Если аномалий нет, для Systeme отдельно применяется `sourceGrowthFactor = 1 + sourceGrowthChange`, где `sourceGrowthChange` — исходное `Кэф. Роста` из TDSheet. Множитель ограничивается 0,5–2 с предупреждением; при отсутствии значения равен 1. Он не заменяет вычисленный тренд. Для IEK такого исходного поля нет, множитель равен 1.

Тренд истории, исходный рост и пользовательский процент применяются последовательно. Они могут описывать пересекающиеся изменения спроса; это прозрачное допущение текущей модели, требующее проверки на истории.

### 3.5. Интеграция по календарному горизонту

Прогноз начинается **на следующий день после `dataThrough`** и заканчивается включительно через `H = leadDays + reviewDays` дней. Для каждого календарного дня берётся сезонный индекс его месяца:

```text
G = 1 + forecastGrowthPercent / 100
seasonalFactor = Σ(s_month(day)) / H
forecastQuantity = max(0,
    baseDailyDemand × trendFactor × sourceGrowthFactor × G
    × Σ(s_month(day)))
```

Частичные месяцы будущего горизонта учитываются по числу вошедших в него дней. Сам прогноз не привязан к текущей системной дате. Выводимые численные поля `DemandForecast` округляются до шести знаков после запятой; ненужные конечные нули убираются.

## 4. Поставки в пути, потребность и округление

`in_transit` — сумма всех **известных** количеств пути. Пустое количество не превращается в подтверждённый ноль: оно исключается из суммы с предупреждением о неполных данных. Отрицательное количество в пути блокирует расчёт товара.

`in_transit_used` — часть известного пути, которая уменьшает заказ:

| Сведения о партии | Текущее правило |
|---|---|
| Известно количество и `expectedBy ≤ dataThrough + H` | Количество вычитается из потребности |
| `expectedBy` позже конца горизонта | Не вычитается; есть предупреждение |
| Количество известно, полная дата прибытия неизвестна | Предполагается поступление внутри горизонта, количество вычитается **с предупреждением** |
| Ожидаемый срок уже прошёл, но партия ещё числится в пути | Количество учитывается как ожидаемое по отчёту; статус требует проверки |
| Количество неизвестно или сведений о пути вообще нет | Неизвестная часть не вычитается; результат предварительный |

У Systeme текст `24.09` не превращается в придуманную полную дату. Поэтому для его известного пути действует предположение о поступлении в пределах горизонта. Оно может уменьшить заказ до нуля; предупреждение в таком случае сохраняется в `review`.

Само количество заказа:

```text
shortage = max(0, forecastQuantity − stock_qty − in_transit_used)
```

Если потребность нулевая, строка не попадает в `items`. Если положительная:

```text
Q0 = ceil(shortage)
Q1 = max(Q0, minimum_shipment_qty), если положительный минимум известен;
     иначе Q0
Q2 = ceil(Q1 / order_multiple) × order_multiple,
     если положительная кратность известна; иначе Q1
order_qty = Q2
```

Для IEK применяется минимальная отгрузка, для Systeme — кратность. Одно условие не подменяет другое. Если условия неизвестны, остаётся округление до целой единицы учёта с предупреждением. Единицы закупки и складского учёта автоматически не конвертируются. **Страховой запас в эту формулу не добавляется**: текущий backend его не рассчитывает.

Срочность определяется по остатку и среднему спросу на горизонте `daily = forecast_qty / H`:

- `high`: остаток ≤ 0 или меньше `daily × leadDays`;
- `medium`: иначе остаток меньше всего `forecast_qty`;
- `low`: остальные случаи.

Это упрощённая приоритизация; даты прибытия отдельных партий внутри горизонта не моделируются по дням.

## 5. Ответ для frontend

Корневой `OrderPlanningResponse`:

| Поле | Что содержит |
|---|---|
| `parameters` | Применённые `leadDays`, `reviewDays`, `historyMonths`, `forecastGrowthPercent`, `anomalyMultiplier` и вычисляемый `horizonDays` |
| `items` | Только товары с положительным рекомендованным заказом |
| `skipped` | Товары, для которых расчёт невозможен из-за данных; есть причины |
| `review` | Расчётные решения «заказ не нужен», у которых есть предупреждения/допущения |
| `excludedSales` | Документы, исключённые из истории успешно рассчитанных товаров; включает товары, которым новый заказ не нужен |
| `suppliers` | Сводка расчёта по каждому выбранному поставщику |
| `warnings` | Общие ограничения и предупреждения источников |

Пустой `items` не означает, что все товары обеспечены запасом. Нужно отдельно показать `skipped` и `review`. Особенно нельзя скрывать `review`, когда заказ стал нулевым из-за пути без подтверждённой даты.

### Поля `items`

Имена ниже — реальные JSON-имена. Поля с аннотацией в модели имеют `snake_case`; вложенный `calculation` и остальные объекты ответа используют `camelCase`.

| JSON-поле | Тип значения | Смысл |
|---|---|---|
| `erp_code` | string | Код 1С |
| `supplier_id` | string | `iek` / `systeme` |
| `supplier_name` | string | Имя поставщика |
| `supplier_article` | string / null | Артикул поставщика |
| `name` | string / null | Наименование |
| `unit` | string / null | Единица количества, если известна |
| `category` | string / null | Исходный код категории |
| `order_qty` | number | Рекомендуемый заказ после условий партии |
| `forecast_qty` | number | Прогноз спроса на горизонт |
| `stock_qty` | number | Остаток, использованный в расчёте |
| `stock_basis` | string | `AVAILABLE_STOCK` или `MONTH_OPENING` |
| `stock_month` | строковое представление YearMonth / null | Месяц начального остатка IEK; для текущего снимка Systeme не задан |
| `in_transit` | number | Все известные количества в пути |
| `in_transit_used` | number | Путь, фактически вычтенный для этого горизонта |
| `minimum_shipment_qty` | number / null | Минимальная отгрузка IEK |
| `order_multiple` | number / null | Кратность Systeme |
| `urgency` | string | `high`, `medium`, `low` |
| `estimated` | boolean | `true`, если остаток оценочный или есть предупреждения строки; это не вероятностная оценка уверенности |
| `calculation` | object | Численные составляющие прогноза, см. ниже |
| `explanation` | string | Обоснование от прогноза до заказа, включая остаток, путь и округление |
| `warnings` | string[] | Допущения и замечания этой строки |

Для ключа строки интерфейса использовать сочетание `supplier_id + erp_code`, а не одно название или номер строки. Неизвестные `supplier_article`, `name`, `unit` нужно корректно отображать; backend не подставляет фиктивные значения.

### `calculation`: `DemandForecast`

| Поле | Смысл |
|---|---|
| `historyFrom`, `historyThrough` | Границы выбранного окна полных месяцев; внутри могут быть исключённые неизвестные месяцы |
| `baseDailyDemand` | Средний дневной спрос после очистки и восстановления, без сезонности |
| `trendFactor` | Подтверждённый тренд последних двух трёхмесячных периодов либо 1 |
| `sourceGrowthFactor` | Применённый рост исходного отчёта либо 1 |
| `seasonalFactor` | Средний сезонный индекс календарных дней будущего горизонта |
| `forecastQuantity` | Прогноз на горизонт; совпадает с `forecast_qty` |
| `stockoutAdjustment` | Количество, восстановленное в истории |
| `excludedOutlierQuantity` | Фактическое уменьшение положительных месячных продаж после очистки, до восстановления stockout |
| `excludedSales` | `SaleAnomaly[]`: аномальные документы, относящиеся к известным месяцам истории |
| `warnings` | Предупреждения самого прогноза; они также включаются в предупреждения строки |

### Документы и сводка исключённых продаж

Одна запись `SaleAnomaly` описывает документ конкретного SKU:

| Поле | Kotlin-тип / JSON | Смысл |
|---|---|---|
| `documentDate` | `LocalDate` / строка `YYYY-MM-DD` | Полная дата документа |
| `documentNumber` | `String` / string | Номер документа; вместе с датой определяет группу строк |
| `quantity` | `BigDecimal` / number | Положительный итог всех известных строк документа с учётом знака |
| `comparisonOrderCount` | `Int` / number | Число остальных полных положительных документов, использованных для сравнения |
| `averageOtherQuantity` | `BigDecimal` / number | Среднее количество этих остальных документов |
| `thresholdQuantity` | `BigDecimal` / number | Это среднее, умноженное на `anomalyMultiplier`; `quantity` строго выше порога |

Корневой `excludedSales` содержит записи `ExcludedSalesSummary`:

| Поле | Kotlin-тип / JSON | Смысл |
|---|---|---|
| `supplierId` | `String` / string | `iek` или `systeme` |
| `productCode` | `String` / string | Код 1С товара |
| `productName` | `String?` / string или null | Наименование |
| `unit` | `String?` / string или null | Единица количества, если известна |
| `excludedQuantity` | `BigDecimal` / number | Равно `DemandForecast.excludedOutlierQuantity` этого товара |
| `sales` | `List<SaleAnomaly>` / array | Документы, исключённые из известных месяцев истории |

В сводку входят только успешно рассчитанные товары с исключениями, включая решения без нового заказа; товары из `skipped` не входят. Сумма `sales[].quantity` может превышать `excludedQuantity`: месячная очистка ограничена доступным положительным количеством. Поэтому для показателя реально исключённых продаж следует суммировать `excludedQuantity`, а документы показывать как объяснение.

### Пропуски, проверка и сводки

`skipped` и `review` содержат одинаковую структуру `SkippedOrderProduct`: `supplierId`, `productCode`, `productName`, `reasons: string[]`. В `skipped` расчёт не завершён; в `review` расчёт выполнен и дал нулевую потребность, но его допущения требуют внимания.

`suppliers` содержит `supplierId`, `supplierName`, `dataThrough`, `productsConsidered`, `recommendations`, `skipped`, `noOrderNeeded`. Счётчики относятся к товарам после фильтра категории. `review` — подмножество `noOrderNeeded`, а не дополнительная категория к общей сумме:

```text
productsConsidered = recommendations + skipped + noOrderNeeded
```

Положительные рекомендации сортируются по поставщику, затем по срочности и коду товара. Категория также возвращается в строке; отдельный объект группировки по категориям не создаётся.

### Пример запроса из frontend

```javascript
// Значения задаёт пользователь; 60 и 30 здесь только пример.
const query = new URLSearchParams({
  leadDays: String(leadDays),
  reviewDays: String(reviewDays),
  historyMonths: '12',
  forecastGrowthPercent: '0',
  anomalyMultiplier: '3',
});
if (supplierId) query.set('supplierId', supplierId);
if (category != null) query.set('category', category);

const response = await fetch(`/api/orders?${query}`);
const result = await response.json();
if (!response.ok) throw new Error(result.detail ?? `Ошибка ${response.status}`);
// Отобразить result.items, result.skipped, result.review,
// result.excludedSales и result.warnings.
```

Существующий frontend пока требует отдельной адаптации: его `GET /api/orders` без обязательных параметров получит `400`; типы ответа нужно расширить для nullable-полей, `review`, `skipped`, `excludedSales` и сводок. Имена дополнительных полей нужно брать из таблицы выше: например, backend возвращает `stock_qty`, а не `free_stock`, и не возвращает `safety_stock`. Контракт загрузки — `POST /api/excel` с именованными полями, а не прежний mock-маршрут `POST /api/imports`. Backend endpoint утверждения `/api/orders/approve` этой реализацией не добавлен.

## 6. Что остаётся ограничением относительно ТЗ

| Ограничение | Что делает текущая версия и чего это не гарантирует |
|---|---|
| Нет обезличенного ID клиента | Выбросы ищутся по документам. Совокупные покупки одного клиента не выявляются |
| Сезонность не связана с транзакциями | Используются общие исходные коэффициенты поставщика. Очистка продаж не означает перерасчёт самих сезонных коэффициентов |
| Нет точных периодов отсутствия товара | Компенсация по нулевым месячным остаткам — оценка. Она не восстанавливает известное число дней stockout |
| Нет текущего свободного остатка IEK | Используется начало месяца, с явной отметкой оценки. Это может завысить или занизить действительную потребность |
| Нет правил категорий | Категория сохраняется и фильтрует выборку, но не меняет целевое покрытие или уровень сервиса |
| Нет нормативных сроков поставки | `leadDays` и `reviewDays` вводятся в запросе; универсальных сроков по умолчанию нет |
| Нет выбора склада | Endpoint использует доступные отчётные срезы и агрегаты; `warehouse`-фильтра и расчёта отдельных складов нет. Сопоставимость складского охвата продаж и остатков требует проверки |
| Неполные количества/даты пути | Используются описанные выше допущения с предупреждениями; результат требует проверки |
| Разные единицы закупки и учёта | Без коэффициента перевода известные проблемные товары пропускаются |
| Непроверенная точность прогноза | Прозрачность формулы и тесты поведения не заменяют бэктест и согласование порогов на данных компании |
| Нет полного рабочего процесса закупщика | Backend не сохраняет правки/утверждения и не отправляет заказ; это следующие этапы |

Поэтому текущую реализацию следует описывать как работающий расчёт рекомендаций с явными допущениями, а не как полное выполнение всех требований ТЗ.

## 7. Проверка на исходных файлах

Полный тест загрузки 12 Excel и расчёта при `leadDays=60`, `reviewDays=30`, `historyMonths=12`, `anomalyMultiplier=3` сохраняет ответ в `build/verification/source-orders.json`. Для данных на 22.09.2026 в сводку исключений попали 1 243 товара и 9 095 позиций «товар в накладной». Это не число уникальных накладных: одна накладная может содержать несколько товаров. Сводка относится только к товарам, для которых выполнен расчёт, и не включает `skipped`.

Например, для IEK `010300001_` исключена накладная `20000119156` от 29.10.2025: количество 65, среднее остальных 11 покупок ≈ 8,64, порог ≈ 25,91. Исходная накладная остаётся в загруженных данных; месячная история для планирования уменьшается на 65.
